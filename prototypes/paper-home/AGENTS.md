# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Accepted prototype direction

Keep the existing KorisLab app separate. Paper is the starting reference, but exact fidelity is no longer required. Use shorter navigation and match rows, the existing KorisLab Array font with its text animation, and its chromatic MetalFx search button. Keep the dashboard glow subdued and symmetric on both sides (zero horizontal shadow offset). The match row must scroll horizontally.

Navigation and match row should be compact with tighter corner radii. Reserve utility icons for Tools and Settings. Keep a visible fixed border around the scrolling match viewport so its clipped right edge is enclosed. Hero typography should be calmer with smaller search guidance. Blend player photos through subdued color and a soft bottom fade using CSS, preserving the original assets.

Match cards should also be narrower horizontally (320 px desktop, 264 px mobile). Use an explicit type hierarchy: subdued venue, prominent tabular time/score, small secondary action. Keep both logos in equal fixed slots, and derive scroll steps from actual card width.

Dashboard framing: remove the yellow upper glow. Use a subdued cool blue-gray haze, with lateral glow masked away from the top and a translucent upper-edge veil. Preserve dashboard legibility.

Keep the hero title, Array subtitle, and supporting description closely grouped: reduce the subtitle gap slightly and the description gap more noticeably.

Navigation has no border. Match cards and the league selector retain a thin dark border; hero frame is also subdued. Include four explicitly sample matches so the final card is partially clipped on desktop, signalling horizontal scrolling.

Match cards must have independent borders: do not draw a shared outline across the gaps between cards. A partially clipped card is intentional in the horizontal scroll viewport.

Upper-page accents should echo the reference dashboard’s warm orange marks: soft warm glow on the Array subtitle, orange gradient pill on navigation hover/focus, and restrained utility/card hover accents. Keep the overall dark surface calm.

The hero dashboard is now an interactive OverviewDashboard component, shared with the #overview page. Keep its dense dark layout and warm orange accents close to the screenshot direction. Use copied 2025–26 team aggregate data; do not invent time series or live results. Team filters, metric selection, ranking/table team selection, and sidebar tabs should work. Existing web app remains separate.

Avoid redundant eyebrow headings such as “Kauden tilannekuva”: use the view title directly. Expanded Overview has no duplicate dashboard topbar. Hero preview extends vertically rather than scrolling internally. Smooth the team-average curve with an orange area glow; use clearly labelled 2P/3P shooting accuracy bars, not unlabeled decorative bars.

Use the original KorisLab navigation, not invented product sections. Näkymä: Etusivu, Yleiskatsaus, Ottelut (count), Joukkueet, Pelaajat, Kausitrendit, Analyysit. Työkalut: Matchup Lab, Custom import, Datan tila. Heittoprofiili is a chart label only, not a navigation section. Unimplemented sections open clearly labelled prototype dialogs.

Hero finishing pass: use warm orange search focus accents instead of purple, readable placeholder contrast, a radial shader mask to calm the texture behind headline/copy, shorter supporting copy, and soft player fades near the dashboard edge. Main heading 68 px, Array subtitle 76 px, search guidance 12 px desktop.

Etusivun jatko: source-backed season insight, expandable analysis example based on season averages, and entry points to teams/players. Navigation is sticky outside the transformed hero canvas and includes a compact working team search. Team entry opens the new nine-team table. Player content remains a clearly labelled prototype dialog. Preserve full-width dashboard preview on mobile through a scoped transform rule.

Kauden nostot ovat erillinen komponentti yleiskatsauksen graafien ja joukkuetaulukon välissä: eniten joukkuepisteitä, paras eFG ja paras nettotehokkuus. Nostojen ensimmäinen mittari on hyökkäyslevypalloprosentti (ORB %), ei pisteet. Jokaisessa nostossa näkyy joukkueen viimeisten enintään viiden ottelun käyrä, vanhemmasta uusimpaan, sekä valitun liigan koko kauden keskiarvo katkoviivana ja lukuna. Lyhyen kauden kohdalla näytetään todellinen ottelumäärä, ei keksittyjä viittä pistettä. Historiallisten naisten 2025–26 otteluiden päivät yhdistetään alkuperäisen sovelluksen schedule.ts-kartasta. Liigan prosenttikeskiarvot lasketaan yhteenlasketuista osoittajista/nimittäjistä; nettotehokkuuden sarjakeskiarvo on 0.

Nostojen graafipisteillä on ottelun päivämäärä, joukkueet, lopputulos ja mittarin arvo tooltipissa (hover, näppäimistöfokus tai mobiilin painallus). Käyrät käyttävät pehmeää täyttöhehkua. Joukkuetaulukossa ovat Sarjataulukko- ja Tehokkuus-välilehdet sekä järjestettävät sarakkeet. Sarjataulukon järjestys perustuu aineiston voittoprosenttiin ja piste-eroon; ei virallisiin tasapistesääntöihin. Taulukon rivin painaminen suodattaa dashboardin joukkueeseen.

Työpöydän datasivun vierityksen tulee toimia myös hiiren ollessa sisältöalueen ulkopuolella (esimerkiksi tyhjä reunus, navi tai sivuvalikko). Ohjaa pystysuuntainen wheel sisältöön vain, jos kohde ei ole oma vieritysalue, avoin dialogi/valikko tai lomakekenttä. Säilytä vaakavieritys ja selaimen zoomaus. Tilasto- ja nostokorteissa ei ole ulospäin osoittavia nuolia, koska niiden toiminto on suodatus, ei navigointi.

Ulkopuolelta ohjatun vierityksen tulee yhdistää rullatapahtumat yhteen requestAnimationFrame-silmukkaan, käyttää lyhyttä aikaan perustuvaa pehmennystä ja reagoida suunnanvaihtoon heti. Peruuta pehmennys, kun käyttäjä siirtyy sisältöalueen omaan vieritykseen tai käyttää hiirtä/näppäimistöä; reduced-motion käyttää välitöntä vieritystä.

Sisältökehys jatkuu ruudun alareunaan ilman pysyvää alapäätyä: alareunus ja alakulmien pyöristys näkyvät vasta sisältöalueen vierityksen lopussa.

Datasivun asetusten edestä poistetaan pystyjakaja. Reduced-motion poistaa sisääntuloliikkeen. Varjostusten uusi viimeistelykierros on vielä tekemättä.
